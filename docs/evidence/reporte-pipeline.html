Reporte del pipeline DevOps de GymTracker API

Repositorio: shotokan/gymtracker-api, rama feat/devops-pipeline. Ejecución de referencia: 41542810593, del 2 de noviembre de 2026, sobre el commit 55512f1.

Resumen ejecutivo

El pipeline funciona de principio a fin en GitHub Actions y no tiene costo. En cada ejecución compila y prueba la API, corre los análisis de seguridad, publica la imagen, provisiona la plataforma con Terraform, despliega en un clúster de Kubernetes, comprueba el escalado y el monitoreo, y ejecuta un DAST contra la aplicación desplegada.

La infraestructura de AWS con EKS está escrita, pero nunca se ha aplicado. Para evitar costos, el entorno de pruebas es un clúster minikube que se crea dentro del runner y desaparece al terminar. Por eso este reporte demuestra el despliegue en ese clúster, y no en la nube. La sección Limitaciones detalla esta y las demás restricciones.

Punto de partida y arquitectura

GymTracker API es una API de entrenamientos en Go con arquitectura hexagonal. Se desplegaba solo como funciones Lambda con AWS CDK, y sus handlers dependen de eventos de API Gateway. La tarea requiere contenedores y Kubernetes, así que se añadió un adaptador sin cambiar la lógica de negocio.

  • internal/httpapi traduce peticiones HTTP a los eventos que esperan los routers existentes, y valida el JWT como lo hacía el authorizer de API Gateway.
  • cmd/server ejecuta toda la API en un solo proceso. El puerto 8080 sirve la API, y el 9090 sirve las métricas y los health checks.
  • El Ingress solo enruta al puerto 8080, así que las métricas no quedan expuestas. El pipeline lo comprueba: /metrics, /healthz y /readyz responden 404 por el Ingress.

El despliegue con Lambda y CDK sigue igual y no comparte infraestructura con el entorno de Kubernetes. El módulo de DynamoDB en Terraform rechaza el nombre de tabla de CDK para evitar colisiones.

Docker

El Dockerfile tiene dos etapas. Las dependencias se descargan en una capa aparte, de modo que quedan en caché hasta que cambie go.mod. La imagen final es distroless, sin shell ni gestor de paquetes, y corre con un UID sin privilegios.

# hadolint ignore=DL3029
FROM --platform=$BUILDPLATFORM golang:1.26.10-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY cmd ./cmd
COPY internal ./internal
COPY pkg ./pkg
ARG TARGETOS=linux
ARG TARGETARCH=amd64
RUN --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w" -o /out/ ./cmd/server ./cmd/dbinit

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/ /app/
USER 65532:65532
EXPOSE 8080 9090
ENTRYPOINT ["/app/server"]

El archivo .dockerignore es una lista de permitidos: solo entran cmd, internal, pkg y los archivos de módulos, sin tests. El archivo compose.yaml levanta la API con DynamoDB Local, y toma el secreto JWT de un .env que git ignora.

El clúster minikube no lo crea Terraform: lo crean la acción del pipeline o scripts/local-up.sh. Terraform provisiona la plataforma sobre él. Los módulos usan variables con validaciones, por ejemplo:

variable "public_access_cidrs" {
  description = "CIDR blocks allowed to reach the Kubernetes API. There is no default on purpose."
  type        = list(string)

  validation {
    condition     = length(var.public_access_cidrs) > 0 && !contains(var.public_access_cidrs, "0.0.0.0/0")
    error_message = "List specific CIDR blocks. The Kubernetes API must not be open to the whole internet."
  }
}

Los tests de terraform test no necesitan credenciales, y comprueban que el plan de AWS se resuelve, que se rechaza una API de Kubernetes abierta y que se rechaza la tabla de CDK. La contraseña de Grafana se genera con random_password, y el estado de Terraform está excluido de git.

Pipeline CI/CD

La definición está en .github/workflows/pipeline.yml. No requiere secretos propios: usa GITHUB_TOKEN. Las acciones de terceros están fijadas por el SHA completo del commit, porque una etiqueta se puede mover.

Monitoreo con Prometheus y Grafana

Terraform instala kube-prometheus-stack. La API publica gymtracker_http_requests_total, gymtracker_http_request_duration_seconds y gymtracker_http_requests_in_flight, etiquetadas por la ruta y no por la URL, para que los identificadores no se conviertan en etiquetas. Un ServiceMonitor las recoge cada 15 segundos.

El dashboard GymTracker API se carga desde un ConfigMap y muestra peticiones por segundo, errores 5xx, réplicas, peticiones por ruta y por código, latencia p50 y p95, réplicas frente al HPA, y CPU y memoria por pod. Hay tres alertas: tasa de errores 5xx superior a 5%, p95 superior a 1 segundo y HPA en el máximo durante 15 minutos.

En esta ejecución Prometheus registró 577 inicios de sesión correctos, y el objetivo de la API estaba activo. El p95 de los últimos 15 minutos fue de 2.25 segundos por la carga de bcrypt, de modo que la alerta de latencia quedó en estado pending, como se espera durante esa prueba.

Seguridad

  • SAST: gosec, govulncheck, gitleaks, hadolint y Trivy pasan en la ejecución de referencia, y cualquiera de ellos detiene el pipeline si encuentra un problema. CodeQL completó su análisis, pero sus alertas se publican en la pestaña Security del repositorio y no detienen el pipeline. Esas alertas no se revisaron para este reporte, porque consultarlas requiere iniciar sesión.
  • Excepciones aceptadas: dos, ambas en Terraform de AWS y con su motivo junto al recurso: el endpoint público de EKS, restringido a una lista de IP, y las subredes públicas, para evitar el costo de NAT. También se ignoran cuatro coincidencias de gitleaks, que son cabeceras JWT de ejemplo en documentación.
  • Secretos: el secreto JWT se genera al desplegar y no está en el repositorio. Las credenciales de DynamoDB Local son valores ficticios que el servicio no comprueba. El token del DAST se oculta en los reportes publicados.
  • DAST: ZAP escaneó la API con autenticación, usando docs/openapi.yaml. El pipeline falla si hay hallazgos de riesgo alto.
RiesgoHallazgo de ZAPDetalle
MedioCross-Domain MisconfigurationAccess-Control-Allow-Origin: * en las rutas de usuarios
BajoServer Error y Application Error Disclosure3 respuestas 500: POST /sessions, y PATCH y DELETE de una rutina cuyo plan no existe. El cuerpo solo dice internal error

Estos hallazgos siguen abiertos. El de CORS requiere decidir qué dominios se permiten en producción, y los 500 deberían ser respuestas 400 o 404.

Cómo replicar y validar

El README tiene las instrucciones completas. La forma más directa no requiere instalar nada: hacer un fork, activar GitHub Actions, cambiar la variable IMAGE del workflow al registro propio y lanzar el workflow Pipeline a mano.

En local, con Docker, curl, jq y AWS CLI:

cp .env.example .env
sed -i.bak "s|^JWT_SECRET=.*|JWT_SECRET=$(openssl rand -hex 48)|" .env && rm .env.bak
docker compose up --build -d
API_URL=http://127.0.0.1:8080 API_HOST=localhost scripts/smoke-test.sh
docker compose down -v

En el entorno de pruebas, además con minikube, kubectl y Terraform:

scripts/local-up.sh
scripts/port-forwards.sh      # en otra terminal
scripts/smoke-test.sh
scripts/hpa-demo.sh
scripts/finops-demo.sh
scripts/local-down.sh --delete

Limitaciones

  • Sin despliegue en la nube. Terraform de AWS solo se validó con proveedores simulados, por decisión de no generar costos. Pueden aparecer errores que únicamente AWS detecta. El overlay de EKS contiene valores por sustituir, como el ID de la cuenta.
  • Entorno de pruebas efímero. Vive dentro del runner durante unos 12 minutos, así que no hay una URL pública que visitar.
  • scripts/local-up.sh sin probar. No se ejecutó de principio a fin en una máquina de desarrollo. Sus pasos corren en el pipeline, salvo minikube image build, porque allí la imagen viene del registro.
  • NetworkPolicy no demostrada. El manifiesto se aplica, pero la red kindnet de minikube no la hace cumplir.
  • Sin TLS. El Ingress del entorno de pruebas usa HTTP. Exponerlo a internet requeriría TLS y límites de peticiones.
  • Datos no persistentes. DynamoDB Local corre en memoria.
  • Rama sin fusionar. El trabajo está en feat/devops-pipeline. Al fusionar en main, también se ejecutará deploy.yml, que despliega Lambda en AWS.
